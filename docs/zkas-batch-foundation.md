# Scoped ZKas batch payment foundation

`lib/zkas/batch-client.ts` talks only to the configured wallet daemon. Its credentialed grant contains the approved account, genesis, application origin, logical ID, exact outputs and fee ceiling. A separate tokenless client starts or polls preparation from the application's own browser context, so the browser supplies its real Origin header; it sends no payment body. The wallet token alone retrieves the version-3 envelope, finalizes the private signer's signatures, refetches finalized bytes after a lost response, and submits the daemon-journaled transaction by logical ID, transaction ID and SHA-256. Responses and signed bytes have fixed bounds and are parsed before use.

`lib/zkas/batch-payment.ts` accepts a wallet-owned private signer handle. The handle must retain the exact prepared envelope and approval it signed, and its `verifyFinalized` method must check the complete canonical transaction, proof, spend and binding signatures, outputs, fee, transaction ID and byte digest. The coordinator calls that verification before writing full signed bytes into the encrypted keyring journal. It changes the local record to `unknown` before the first submit call; a timeout leaves those bytes and identifiers intact for the same-byte retry. The daemon keeps its own durable journal and broadcasts its copy of the bytes. The application never receives the wallet token, viewing key, seed or signer handle.

The encrypted batch journal and legacy payment journal share a serialized account reservation gate in the extension background context. A new batch cannot overlap an unresolved legacy send, and a legacy send cannot overlap any retained batch record. A manual legacy warning clear cannot release a `submitting` or `uncertain` send. The batch journal deliberately has no manual clear or time-based release. Account selection, daemon URL, origin permissions and the current keyring session must be checked by the wallet integration before and after each asynchronous step.

This is a foundation only. No provider, page, seed factory, browser signer artifact, receive/history bridge or funded send is wired to it yet. Current daemon grants accept HTTPS application origins; HTTP loopback application origins remain blocked pending a separately reviewed daemon change. If the extension loses its encrypted local journal, the present daemon API cannot list batch logical IDs; do not infer safety from an empty local journal. A crash after daemon finalization but before local persistence also needs a separately reviewed credentialed recovery path that can independently verify those bytes after recreating the private signer. Until then, recovery must fail closed and must not create a fresh logical payment or fee. The local batch reservation currently covers every retained record, including a returned terminal status; it does not implement multi-message release. A later increment must require positive selected-chain acceptance, complete wallet reconciliation and reorg-safe terminal revalidation before releasing a reservation.
