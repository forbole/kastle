# Scoped ZKas batch payment foundation

`lib/zkas/batch-client.ts` talks only to the configured wallet daemon. Its credentialed grant contains the approved account, genesis, application origin, logical ID, exact outputs and fee ceiling. A separate tokenless client starts or polls preparation from the application's own browser context, so the browser supplies its real Origin header; it sends no payment body. The wallet token alone retrieves the version-3 envelope, finalizes the private signer's signatures, refetches finalized bytes after a lost response, and submits the daemon-journaled transaction by logical ID, transaction ID and SHA-256. Responses and signed bytes have fixed bounds and are parsed before use.

`lib/zkas/batch-payment.ts` accepts a wallet-owned private signer handle. The handle retains the exact prepared envelope and approval it signed. Kastle exports its original signature ticket into the encrypted keyring journal before calling daemon finalization. After a restart, a new handle must be created from the current wallet-local seed and the retained approval, then import that ticket without signing again. Recovery first refetches finalized bytes by the known logical ID. If finalization had not completed, it retries only the ticket's original daemon session and signature map. The handle's `verifyFinalized` method must check the complete canonical transaction, proof, spend and binding signatures, outputs, fee, transaction ID and byte digest. The coordinator calls that verification before writing full signed bytes into the encrypted keyring journal. It changes the local record to `unknown` before the first submit call; a timeout leaves those bytes and identifiers intact for the same-byte retry. A missing or invalid ticket, unavailable daemon result, or failed verification keeps the account reserved. The daemon keeps its own durable journal and broadcasts its copy of the bytes. The application never receives the wallet token, viewing key, seed, ticket or signer handle.

The encrypted batch journal and legacy payment journal share a serialized account reservation gate in the extension background context. A new batch cannot overlap an unresolved legacy send, and a legacy send cannot overlap any retained batch record. A manual legacy warning clear cannot release a `submitting` or `uncertain` send. The batch journal deliberately has no manual clear or time-based release. Account selection, daemon URL, origin permissions and the current keyring session must be checked by the wallet integration before and after each asynchronous step.

This remains an unwired foundation. No provider, page, wallet-local seed factory, browser signer artifact loader, receive/history bridge or funded send is connected to it. The wallet integration must recheck the selected account, address, genesis, application grant, configured daemon and current keyring unlock generation around every awaited step; the unlock generation is a session fence, not a persisted identity. Batch application origins retain the existing HTTPS policy. HTTP is accepted only for literal lowercase `localhost` or `127.0.0.1` with an explicit canonical port from 1 to 65535 other than 80; the browser's actual Origin must still match the approved string and the daemon's CORS allow-list must permit it. This application-origin policy does not change the separately configured daemon URL or legacy wallet connection policy. A preexisting `preparing` record without a ticket cannot be signed again after restart. If the extension loses its encrypted local journal, do not infer safety from an empty local journal or a daemon listing without the original approval. The local batch reservation covers every retained record, including a returned terminal status; it does not implement multi-message release. A later increment must require positive selected-chain acceptance, complete wallet reconciliation and reorg-safe terminal revalidation before releasing a reservation.

The credentialed client now has a bounded journal-inventory reader for the wallet daemon's proposed `submit-many/records` route. It uses only the configured daemon and wallet token, gathers up to 4,096 records in 32-entry pages, requires a consistent epoch and opaque unlisted-reservation count during each complete walk, and rejects malformed or changing pages. A continuation page must contain at least one record, even when it is the final page; an empty first page remains valid. The daemon route is not deployed as part of this client increment. The reader does not reconcile a transaction, release the local account reservation, expose a wallet token to an application, or infer safety from an empty page. A future release flow must take a fresh complete inventory after exact-ID status calls: even a settled status call updates the daemon journal revision and changes its epoch. Each walk must be internally stable, while the two walks may have different epochs; immutable logical IDs, transaction IDs and byte digests must match. A later daemon grant must still independently recheck all viewing-key reservations. The existing 128-record encrypted journal limit remains.
