# Private direct first-use payment admission

The first MatJam action for a freshly born wallet has no prior signed batch ticket. `beginDirectFirstUse` is a separate wallet-private path; the ordinary `reserveAfterFreshSettlement` rule still rejects an empty payment history. The future privileged factory must supply the immutable wallet-issued birth and a fresh, ready `session-from-birth` actor through `assertReadyFromBirth`. While the shared account gate is held, the payment coordinator reads two complete credentialed daemon inventories for the exact selected account and genesis. Both must contain zero listed records and zero unlisted reservations before the original four-output action and native approval are written to the encrypted keyring-backed batch journal. Only then may the daemon issue a preparation capability; the background does not call the preparation POST.

The journal retains the exact approved intent, action ID, idempotency key, peer/card, birth/session/source binding, and native sealed digest. It accepts the three 1-sompi MatJam outputs and the 10,000,000-sompi zero-memo collector output with at most 5,000,000 sompi of network fee. A failed grant can regrant only this original pending record after fresh private fences; a newly detected legacy reservation blocks retry. Restarted completion pins the first prepared session and checksum before a signer opens. A different prepared session or checksum cannot be signed, and a signed ticket still takes the existing recovery path.

This slice does not itself witness a birth, lease a source, perform the human popup, persist a peer pin, or sign a payment. The private action factory must provide those authorities and verify the selected actor again after pin persistence invalidates its old lease. Tests cover first-use denial/positive reservation, two empty inventories, malformed official effects, lost-grant retry, legacy conflict, and prepared-session substitution; existing batch controls remain in force.
