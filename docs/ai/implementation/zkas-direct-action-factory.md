# Private direct action coordinator

The wallet background factory is the only caller of MatJam's native direct review and seal methods. It keeps the opaque review token and selected-account actor in memory while the popup displays the native-normalized action, recipient card, four output addresses, 10,000,003-sompi explicit payment, 5,000,000-sompi network-fee ceiling, and 15,000,003-sompi maximum. The requesting page supplies only an invite card and note, an invitation decision, or text. The wallet fixes the fee and daemon.

Before allocating a native review, the factory checks the encrypted account journal. An unresolved original blocks a replacement action. If that original already has its signed ticket and full finalized bytes, the factory may freshly reconcile its settlement first: it replays from the same birth and uses the existing two credentialed inventories, original ticket import, full-byte verification, exact-ID settled status, and account gate before marking only that stored original settled. A missing proof leaves it unresolved and no new action ID is allocated. It repeats the account check after human approval and before native sealing. After approval, the factory independently replays the same immutable session birth from its fixed daemon/index, reviews the same input again, and compares every authority-bearing review field apart from the random action ID/token and an append-only selected head. It then witnesses that the retained reviewed head remains selected before asking native code to seal. A changed account, grant, pin set, daemon pairing, source generation, birth, recipient card, reference, normalized text, address, or amount blocks sealing. The native sealed-output decoder and factory both bind the four roles and exact addresses/amounts to the popup review.

The final settlement journal write and the next native review use the ordinary wallet-settings then settings writer locks. The wallet compares the original selected account, exact address, daemon, and retained birth inside those short barriers; daemon inventory requests and signature verification happen before the terminal locks. A confirmed lookup for the same selected original releases only its matching in-memory approval slot. A null lookup or a result for another action does not release it.

The sealed output, approved pin, and encrypted original action record are stored privately before a capability is returned. Saving the pin intentionally closes the old receive actor. The factory permits that one pin generation change, then checks the original daemon pairing, grant generation and revision, wallet session, connection generation, account, birth, and source against the reopened actor before grant. A fresh account's first paid action requires ready session-from-birth and two complete, empty, credentialed daemon inventories under the shared account gate. Later actions require fresh settled verification of every retained signed ticket and finalized transaction, two complete inventories, and exact daemon statuses. The ordinary full-history payment admission is unchanged. The page performs the empty-body prepare POST; the background never prepares in response to approval or a status poll.

The journal keeps the original action ID, logical ID, exact sealed digest, selected birth/session, card, four memo outputs, and prepared session/checksum. A worker restart can discover one unresolved original for the selected account and website, regrant its original intent, or complete its original prepared/signed ticket. It cannot mint a replacement action or fee. UNKNOWN retains the original ID. A clean human rejection returns failed only before approval starts; concurrent cancellation after that point is unknown. Status checks do not sign or submit. A daemon-confirmed status alone cannot free the account; pre-review reconciliation first proves and records the original settlement. The next paid admission independently re-verifies prior signed bytes and daemon evidence.

This is a bounded trial path: every receive/review replays from birth within the native 128-page/4,096-block window. A gap, source change, lost birth, or exhausted limit is unavailable. Session-from-birth does not mean complete account history or prove absence of pre-birth notes. The synthetic factory control verifies ordering, credential headers, and changed-output rejection; the separate account-admission control uses the actual journal/payment classes to check restart and pairing-mutation boundaries with synthetic native/history/transport. Neither proves funded consensus, raw-note cryptography, or live daemon availability. The separate pinned-WASM and raw-body fixtures cover their stated native boundaries. Manual two-wallet verification must install the final build before birth enrollment, fund after birth, then settle invite, decision, and text at least 600 DAA each within the same bounded suffix.
